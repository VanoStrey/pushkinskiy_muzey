# Персональный AI-маршрут по Пушкинскому музею

Веб-сервис, который собирает персональный маршрут по Главному зданию Пушкинского музея: посетитель описывает, кто он, сколько у него времени и что ему интересно, а сервис подбирает 4–6 экспонатов из официального каталога музея, объясняет, почему выбрал каждый из них, и превращает маршрут в пошаговый сценарий с интерактивной картой залов.

Стек: **FastAPI** (Python 3.12) + **React 19 / Vite / TypeScript / Tailwind** + **YDB** + **Yandex AI Studio**. Локально — Docker Compose, в облаке — Cloud Function, Object Storage и API Gateway за одним HTTPS-доменом.

## Возможности

- **Форма предпочтений.** Интересы (до четырёх тем), длительность визита, состав компании, уровень знакомства с искусством, формат маршрута, комментарий гостя и необязательная пауза на отдых.
- **Персонализация от AI Studio.** Модель получает только проверенные записи каталога, выбирает остановки, пишет причину выбора и задание-наблюдение для каждой.
- **Защита от выдуманных экспонатов.** Ответ модели проверяется: каждый ID должен входить в переданные кандидаты, повторов быть не должно, а названия, авторы, даты, залы и инвентарные номера всегда берутся из каталога музея, а не из текста модели.
- **Интерактивная карта залов.** Официальные векторные планы этажей, центроиды залов, маркеры остановок, переключение этажей, масштабирование и переход по клику.
- **Пошаговое прохождение.** Карточка экспоната с увеличением изображения, зал и этаж, персонализированное объяснение, задание, переходы «назад / далее» и пауза на кофе между этажами.
- **Продолжение с того же места.** Прогресс сохраняется в браузере: перезагрузка страницы не начинает маршрут заново.
- **Отказоустойчивость.** Без настроенной AI Studio сервис отдаёт нейтральный маршрут из каталога, а не ошибку; без YDB каталог и маршруты продолжают работать.
- **Проверка уникальности.** Сравнение маршрута с официальными программами музея: совпадение последовательности, перестановка, существенное пересечение или сходство названий.

## Быстрый старт

Нужны только Docker и git.

```bash
cp .env.template .env
docker compose up -d
```

Откройте http://localhost:5173/ и пройдите маршрут: выберите интересы и время → получите маршрут → откройте карту → листайте остановки → завершите визит.

Чтобы AI Studio действительно персонализировал маршрут, впишите в `.env` ключ и каталог:

```
YANDEX_API_KEY=ваш_ключ
YANDEX_FOLDER_ID=ваш_каталог
```

Без них приложение работает: каталог и интерфейс открываются, а маршрут строится в резервном режиме (`is_fallback: true`). В облаке ключ не нужен — функция авторизуется IAM-токеном сервисного аккаунта.

Полезные адреса при локальном запуске:

| Адрес | Что это |
| :-- | :-- |
| http://localhost:5173/ | приложение |
| http://localhost:5173/api/docs | Swagger UI |
| http://localhost:5173/api/hello | статус YDB и ответ модели |
| http://localhost:5173/api/exhibits | каталог Главного здания |
| http://localhost:8765 | веб-интерфейс YDB |

Подробности, включая запуск без Docker и решение типовых проблем, — в [DEVELOPMENT.md](docs/DEVELOPMENT.md).

## Как это устроено

```
Браузер (SPA, один экран)
  │  относительные запросы /api/...
  ▼
API Gateway                    Локально: Vite dev-server с прокси /api
  ├─ /api/*  → Cloud Function   (FastAPI: api → services → repositories → data)
  └─ /*      → Object Storage   (frontend/dist)
                    │
                    ├──▶ YDB Serverless: official_routes
                    └──▶ Yandex AI Studio (OpenAI-совместимый API)
```

Ключевые решения:

- каталог музея — JSON-снимок внутри бандла функции, поэтому локально и в облаке поведение одинаково и не нужны миграции;
- единственный источник фактов — официальные данные музея, модель только выбирает и объясняет;
- бэкенд не хранит состояние между запросами, весь долговременный снимок живёт в YDB;
- фронтенд не знает адресов бэкенда — только относительный префикс `/api`, поэтому CORS не настраивается ни локально, ни в облаке.

Подробный разбор — в [ARCHITECTURE.md](docs/ARCHITECTURE.md).

## API

Все эндпоинты живут под префиксом `/api`; полные контракты — в [API.md](docs/API.md).

| Метод и путь | Назначение |
| :-- | :-- |
| `POST /api/route/generate` | основной сценарий: персональный маршрут для интерфейса |
| `POST /api/routes/generate` | каталожный вариант: маршрут по зданию и аудитории |
| `GET /api/exhibits` | каталог экспонатов здания |
| `GET /api/routes/official` | официальные маршруты музея, сопоставленные с каталогом |
| `POST /api/routes/check-uniqueness` | сравнение маршрута с официальными программами |
| `POST /api/routes/import-official` | повторный импорт официальных маршрутов |
| `POST /api/ai/ask` | демонстрационный вызов модели |
| `GET /api/hello` | проверка живости, статус YDB и AI Studio |

Пример:

```bash
curl -X POST http://localhost:5173/api/route/generate \
  -H 'Content-Type: application/json' \
  -d '{"interests":["загадки","древний мир"],"duration_minutes":90,"group_type":"friends","style":"quest"}'
```

## Данные музея

Приложение работает со снимком открытых данных музея: **97 экспонатов, 11 зданий, 61 зал**, из них **27 записей пригодны для маршрутов Главного здания** (`building_id=116`, значение по умолчанию). Тексты музея показываются фрагментами до 500 символов со ссылкой на первоисточник, изображения загружаются по URL музея и не копируются в репозиторий — это соответствует [правилам использования материалов музея](https://pushkinmuseum.art/usage_policy/index.php?lang=ru).

```bash
python backend/scripts/prepare_museum_data.py            # пересобрать каталог из data/raw/ (офлайн)
python backend/scripts/prepare_museum_data.py --update   # скачать свежие выгрузки музея и пересобрать
```

Полные исходники в `data/raw/` не включены в репозиторий; после клонирования приложение сразу использует подготовленные JSON из `backend/app/data/processed/`. Форматы, правила отбора и проверка уникальности описаны в [DATA.md](docs/DATA.md).

Источники: [наборы открытых данных Пушкинского музея](https://pushkinmuseum.art/open_data/index.php?lang=ru), [правила использования материалов и изображений](https://pushkinmuseum.art/usage_policy/index.php?lang=ru).

## Разработка

```bash
cd backend  && uv sync && uv run pytest     # тесты бэкенда
cd backend  && uv run uvicorn app.main:app --port 8000
cd frontend && npm ci && npm run dev        # фронтенд на :5173
cd frontend && npm run lint && npm run build
```

Две особенности, о которых стоит знать сразу:

- в контейнеры смонтированы только `backend/app` и `frontend/src`; после добавления зависимостей и правки конфигов нужен `docker compose up -d --build`;
- два теста в `backend/tests/test_museum_data.py` читают `data/raw/`, которого нет в клонированном репозитории. Чтобы они проходили (и чтобы CI не остановился на этом шаге), выполните `python backend/scripts/prepare_museum_data.py --update`.

Все переменные окружения описаны в [DEVELOPMENT.md](docs/DEVELOPMENT.md#4-переменные-окружения) и в `.env.template`.

## Деплой в облако

Схема работы: браузер → API Gateway (`https://<id>.apigw.yandexcloud.net`), где `/api/*` уходит в Cloud Function, а всё остальное — в бакет Object Storage с `frontend/dist`. Фронтенд и API живут на одном HTTPS-домене, CORS не нужен, свой домен не требуется.

Путь команды — три шага:

1. **Создать репозиторий из шаблона** в SourceCraft. Конфигурация CI (`.sourcecraft/ci.yaml`) приедет вместе с кодом.
2. **Создать сервисное подключение** в организации команды (**Настройки → Сервисные подключения**): имя `default-service-connectionXX` (XX — номер команды), сервисный аккаунт с ролью `editor` на каталог. Ключи нигде не хранятся — доступ идёт через федерацию удостоверений. **Впишите актуальное имя подключения в `.sourcecraft/ci.yaml` → `tokens.yc.service_connection`**, иначе деплой не сработает.
3. **Запустить CI** — push в `main` (или перезапуск пайплайна). CI сам создаст недостающие ресурсы и обновит остальные: YDB Serverless `hackathon-app-db`, функцию `hackathon-app-api` (Python 3.12, 256 МБ, таймаут 60 с), закрытый бакет `hackathon-app-<ID каталога>` и API Gateway `hackathon-app-gw`.

Первыми шагами CI идут `pytest` бэкенда, `npm run lint` и `npm run build`: если что-то упало, деплой останавливается и в облаке остаётся предыдущая рабочая версия.

В логе шага `deploy-gateway` есть строка `App URL: https://<id>.apigw.yandexcloud.net/` — тот же адрес виден в консоли: **API Gateway → hackathon-app-gw → Домен**. На странице работает `/api/hello`, который покажет статус YDB и ответ модели; в логах функции (**Cloud Functions → hackathon-app-api → Логи**) должна быть строка `YDB connection succeeded`.

Добавление своей переменной окружения (флага или секрета) описано в [DEVELOPMENT.md](docs/DEVELOPMENT.md#4-переменные-окружения) и в `.sourcecraft/ci.yaml`: несекретные значения задаются в `config.py` и `env` workflow, секреты — в **Настройки репозитория → Секреты** SourceCraft и передаются в `--environment`.

## Главный принцип

**Простое лучше сложного.** На хакатоне баллов дают за работающий продукт, а не за архитектурную сложность: лишние слои, очереди и кэши только отнимают время. Тот же принцип закреплён в [`AGENTS.md`](AGENTS.md) — и AI-ассистент следует ему при изменениях в репозитории.

## Ограничения

- Каталог — снимок из 97 записей, а не полный фонд музея; часть произведений в официальных маршрутах в него не попадает.
- Признаки `show_in_hall` и закрытия зданий взяты из выгрузки музея и не подтверждают доступность экспоната сегодня.
- Порядок маршрута тематический: кратчайший путь не рассчитывается.
- Задания — наблюдения без правильного ответа; тип викторины сохранён в схеме, но не используется.
- Таймаут облачной функции — 60 секунд, поэтому вызов модели ограничен 50 секундами, а состояние между запросами не сохраняется.
